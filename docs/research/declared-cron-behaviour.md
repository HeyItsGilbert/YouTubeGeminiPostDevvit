# How declared `scheduler.tasks` crons behave on install and upgrade

Research for ticket [#33](https://github.com/HeyItsGilbert/YouTubeGeminiPostDevvit/issues/33) (map [#28](https://github.com/HeyItsGilbert/YouTubeGeminiPostDevvit/issues/28)). The question is whether a Devvit Web `devvit.json` cron can replace `ensureCheckerScheduled` (`src/checkerSchedule.ts`), and what happens to the `check_new_episodes` job (`*/30 * * * *`) that the Blocks version created at runtime.

Sources: Devvit docs as of 2026-10-25, the installed `@devvit/*` 0.14.8 packages (identical code on unpkg), older npm releases for comparison, and upstream `reddit/devvit` source at 0.15.0. Anything not shown directly by a source is marked **[INFERENCE]**.

## Answer

- **Reconciliation runs inside the app, not on the platform.** When any task in `devvit.json` has a `cron`, the build adds `AppInstall` and `AppUpgrade` handlers to the app bundle. On each of those events the handler cancels every existing cron job whose manager is `DEVVIT_JSON` or `MANAGER_UNSPECIFIED`, then schedules one job per declared cron task with manager `DEVVIT_JSON`.
- **Per install, recreated on every upgrade, deduplicated by cancel-all-then-recreate.** Nothing deduplicates by name. Nothing reconciles outside install and upgrade.
- **Same weakness as today.** If an install or upgrade trigger never fires, the declared cron is never created. This is the failure mode the current heal logic exists to cover.
- **The old Blocks job survives the migration.** Since 0.14.6, Blocks `runJob` tags jobs `USER`, and the reconciler never touches `USER` jobs. A leftover `check_new_episodes` cron would keep firing next to the declared one. If the declared task is also named `check_new_episodes`, both jobs call the same endpoint on the same `*/30` schedule, so the checker runs twice at once. The migration must cancel the leftover in code.
- **Visible and cancellable.** Declared crons appear in an unfiltered `listJobs()` and in `listJobs([DEVVIT_JSON])`. The public `cancelJob(id)` sends no manager check from the client. A cancelled declared cron stays gone until the next install or upgrade.
- **Constraints.** Five-field cron runs at most once per minute. Six-field (per-second) cron is experimental. Each install can have at most 10 live recurring actions. A task can carry a static `data` object, delivered as `TaskRequest.data`.

## Findings per question

### 1. Auto-created per install?

**Yes, by the app's own `AppInstall` handler.**

- Docs: "Jobs configured with `cron` in `devvit.json` are rescheduled on installation and upgrade" ([Scheduler, "Managing recurring jobs across deployments"](https://developers.reddit.com/docs/capabilities/server/scheduler.md)).
- Mechanism: the build-time template `configureScheduler` calls `Devvit.addSchedulerJob` for every task. Its handler POSTs `{ name, data }` to `task.endpoint`. If any task has `cron`, it also calls `Devvit.addTrigger({ events: ['AppInstall', 'AppUpgrade'], … })` to do the scheduling ([`blocks.template.ts` L244-L329 @ 0.15.0](https://github.com/reddit/devvit/blob/4c7dc0304bf3b3dd281a204b80735c0f733a9539/packages/build-pack/src/esbuild/templatizer/blocks.template.ts#L244-L329); installed copy `node_modules/@devvit/build-pack/esbuild/templatizer/blocks.template.js` L178-L245, 0.14.8). The bundle declares the install/upgrade trigger capabilities only when some task has a cron ([`dependency-spec-util.ts` L178-L185](https://github.com/reddit/devvit/blob/4c7dc0304bf3b3dd281a204b80735c0f733a9539/packages/build-pack/src/esbuild/dependency-spec-util.ts#L178-L185)).
- The template is used for Devvit Web and Blocks bundles alike; it is the entry generated by `templatize()` (`node_modules/@devvit/build-pack/esbuild/templatizer/templatizer.js`).
- **Consequence [INFERENCE]:** a declared cron is exactly as reliable as `AppInstall`/`AppUpgrade` delivery. The app saw installs end up with "no job and no log" (`src/checkerSchedule.ts` header). A declared cron would hit the same gap, because no platform-side reconciler exists in any source checked. The template logs `Cron task '<name>' scheduled.` at VERBOSE severity, and `Failed to schedule <name>: …` at ERROR, so `devvit logs` can show whether it ran.

### 2. Re-created / updated on upgrade?

**Yes.** On every `AppUpgrade`, all `DEVVIT_JSON` and `MANAGER_UNSPECIFIED` cron jobs are cancelled and the declared ones are scheduled again with their current `cron` and `data`. Editing the cron string in `devvit.json` and uploading a new version replaces the schedule. Docs: "Devvit replaces configuration-managed recurring jobs with the configured schedules" ([Scheduler](https://developers.reddit.com/docs/capabilities/server/scheduler.md)).

Caveat: if you remove the **last** cron task, the trigger is no longer registered, so old jobs are not cancelled. Docs: "In Devvit 0.14.8, removing the final `cron` task from `devvit.json` does not automatically cancel the previously configured jobs" ([Scheduler](https://developers.reddit.com/docs/capabilities/server/scheduler.md)). The source matches: the trigger is added only `if (Object.keys(cronTasks).length > 0)`.

### 3. Deduplicated?

**Only by cancel-all-then-recreate on each install or upgrade.** No source shows deduplication by name or schedule.

- Repeated upgrades do not pile up jobs, because every reconciliation cancels its own earlier jobs first.
- The cancel and schedule calls run in `Promise.all` inside one handler, with no lock. [INFERENCE] Two reconciliations running at once (for example `AppInstall` and `AppUpgrade` in quick succession) could each schedule a copy. Nothing seen suggests the platform does this.
- Known platform bug: [reddit/devvit#239](https://github.com/reddit/devvit/issues/239) (open). After uninstall and reinstall, a "ghost" copy of a `devvit.json` cron kept running, invisible to `listJobs()` and impossible to cancel. The app cannot fix this.

### 4. Visible to `listJobs`?

**Yes.**

- `scheduler.listJobs(managers = [])` with no filter "will apply no filters", so it returns jobs from every manager. `listJobs([ScheduledActionManager.USER])` excludes declared crons. Docs: "`ScheduledActionManager.USER` selects jobs managed by your app code … Calling `listJobs()` without a filter returns jobs from all managers" ([Scheduler](https://developers.reddit.com/docs/capabilities/server/scheduler.md)). Client source: [`@devvit/scheduler@0.14.8/SchedulerClient.js`](https://unpkg.com/@devvit/scheduler@0.14.8/SchedulerClient.js) L43-L76.
- The listed entry does **not** expose the manager. It has `{ id, name, cron, data }` for crons and `{ id, name, runAt, data }` for one-offs (same file). The only way to tell a declared cron from a runtime one is to query once per manager.
- Manager enum: `MANAGER_UNSPECIFIED = 0` ("created before this field existed"), `DEVVIT_JSON = 1` ("Devvit may cancel or reschedule to keep in sync with config"), `USER = 2` ("Devvit should neither cancel nor schedule") ([`@devvit/protos@0.14.8` scheduler.d.ts](https://unpkg.com/@devvit/protos@0.14.8/json/devvit/plugin/scheduler/scheduler.d.ts) L10-L21).
- Open bug [reddit/devvit#259](https://github.com/reddit/devvit/issues/259): on one Blocks app, `listJobs()` returned `[]` immediately after `runJob()` and the jobs never ran. It is unresolved, and it is about runtime jobs, not declared ones.

### 5. Cancellable at runtime?

**Yes, from the client side. Server-side enforcement is unconfirmed.**

- `cancelJob(jobId)` sends `Cancel({ id })` with no manager argument ([`SchedulerClient.js`](https://unpkg.com/@devvit/scheduler@0.14.8/SchedulerClient.js) L39-L42). The template itself cancels `DEVVIT_JSON` jobs through this same public `scheduler.cancelJob`, which shows that the public client can cancel them.
- After cancellation the job stays gone until the next `AppInstall`/`AppUpgrade`. Nothing else re-creates it (source above).
- **App code cannot re-create a `DEVVIT_JSON` job.** Public `runJob` always sends `manager: USER` ([`SchedulerClient.js`](https://unpkg.com/@devvit/scheduler@0.14.8/SchedulerClient.js) L26-L37). The template uses the raw plugin with the comment "we need to schedule apps with a manager other than USER". A runtime "heal" can only create a `USER` job, and the reconciler will never clean that job up.

### 6. Minimum interval

- Standard five-field cron: "Scheduled jobs currently perform one scheduled run per minute", so the minimum is 1 minute ([Scheduler, "Faster scheduler"](https://developers.reddit.com/docs/capabilities/server/scheduler.md)).
- Six-field cron with seconds (`*/30 * * * * *`) is **experimental**, and actual frequency "will depend on how long the job takes to complete" (same section). The `devvit.json` schema accepts both forms in `scheduler.tasks.*.cron` ([config docs](https://developers.reddit.com/docs/capabilities/devvit-web/devvit_web_configuration.md); schema `$defs.CronSchedule` in `node_modules/@devvit/shared-types/schemas/config-file.v1.json`).
- Limits per installation: at most **10 live recurring actions**; at most 60 `runJob()` calls per minute; at most 60 deliveries per minute ([Scheduler, "Limitations"](https://developers.reddit.com/docs/capabilities/server/scheduler.md)). [INFERENCE] Declared crons probably count toward the 10, since they are ordinary scheduled actions, but no source says so. The app needs 1.
- `*/30 * * * *` is well within all of these.
- The endpoint must match `^/internal/.+` (schema `$defs.InternalEndpoint`).

### 7. Job data

- A cron task may carry a static `data` object: `AppSchedulerTaskConfig = { endpoint: string; cron?: string; data?: JsonObject }` ([`config-file.v1.ts` L165-L170](https://github.com/reddit/devvit/blob/4c7dc0304bf3b3dd281a204b80735c0f733a9539/packages/shared-types/src/schemas/config-file.v1.ts#L165-L170)). The JSON schema allows `data` only on the variant that has `cron`: "Optional data to pass to a cron-based task when it runs."
- The handler receives `TaskRequest { name, data }`. "In the case of cronjobs, this will be the value specified in `devvit.json`" ([`@devvit/scheduler@0.14.8` types/scheduler.d.ts](https://unpkg.com/@devvit/scheduler@0.14.8/types/scheduler.d.ts) L62-L71).
- The data is fixed per version: it can change only by editing `devvit.json` and upgrading. A run with no `data` gets `data: undefined`.
- One-off `runJob({ name: 'check_new_episodes', runAt, data: { forceRepost, manual: true } })` calls, as `src/main.ts` does for manual checks, keep working against the same task name. The task entry registers the handler whether or not it has a cron, and the reconciler cancels only entries that have `cron`. The handler should treat a missing `data` as a scheduled run.

### 8. Coexistence with the leftover runtime `check_new_episodes` job

What the Blocks version leaves behind:

- `@devvit/public-api` ≤ 0.13.5 and `@devvit/scheduler` 0.14.5 sent **no** `manager` ([public-api 0.13.5 SchedulerClient.js](https://unpkg.com/@devvit/public-api@0.13.5/apis/scheduler/SchedulerClient.js) L20-L30; [scheduler 0.14.5](https://unpkg.com/@devvit/scheduler@0.14.5/SchedulerClient.js) L26-L30). Jobs created by those versions are `MANAGER_UNSPECIFIED`.
- `@devvit/scheduler` ≥ 0.14.6 (published 2026-09-28) sends `manager: USER`. Blocks 0.14.x `context.scheduler` is that same client (`@devvit/public-api@0.14.8` `apis/makeAPIClients.js` imports `scheduler` from `@devvit/scheduler`).
- The app has been on 0.14.6+ since commit `6695782` (2026-09-29). Its `AppUpgrade` handler (`ensureCheckerScheduled(context, 'reset')`) cancels and re-creates the checker cron on every upgrade. [INFERENCE] On any install whose last upgrade trigger fired, the live `check_new_episodes` cron is therefore `USER`-managed. Installs that missed upgrade triggers may still hold an older `MANAGER_UNSPECIFIED` job, or a `USER` job created by a heal.

What happens after upgrading to a Web build that declares the cron:

| Leftover job manager | Template reconciler on `AppUpgrade` | Result |
|---|---|---|
| `MANAGER_UNSPECIFIED` (≤ 0.14.5) | cancelled (it filters `DEVVIT_JSON` + `MANAGER_UNSPECIFIED`) | Clean: only the declared cron remains |
| `USER` (≥ 0.14.6, the expected case) | **untouched** | **Two crons**, both `*/30` |

With two crons:

- If the declared task keeps the name `check_new_episodes`, both jobs dispatch to its endpoint. The scheduler dispatches by `action.type`, which is the job name ([`@devvit/public-api@0.14.8` internals/scheduler.js](https://unpkg.com/@devvit/public-api@0.14.8/devvit/internals/scheduler.js) L6-L11), and the template registers its handler under the task name. So the checker runs twice at the same minute, which can double-post. [INFERENCE: depends on the checker's own idempotency]
- If the declared task gets a different name, the leftover `check_new_episodes` job has no handler. `handleScheduledAction` throws `Job check_new_episodes not found` every 30 minutes until the job is cancelled.

Ordering: the template's reconciler and the app's own `onAppUpgrade` endpoint are both handlers for the same event. They run concurrently via `Promise.allSettled` ([`@devvit/public-api@0.14.8` internals/triggers.js](https://unpkg.com/@devvit/public-api@0.14.8/devvit/internals/triggers.js) L9-L28). A cleanup that touches only `USER` jobs cannot race with the reconciler, which touches only `DEVVIT_JSON`/`MANAGER_UNSPECIFIED` jobs.

Docs: "Starting with Devvit 0.14.6, recurring jobs created in app code are preserved across deployments … The job keeps its stored schedule and data until your app cancels it" ([Scheduler](https://developers.reddit.com/docs/capabilities/server/scheduler.md)). Before 0.14.6 the reconciler cancelled **every** cron job, whatever its manager ([`@devvit/build-pack@0.14.5` blocks.template.js](https://unpkg.com/@devvit/build-pack@0.14.5/esbuild/templatizer/blocks.template.js) L195-L214). That old behaviour would have removed the leftover automatically. It no longer does.

**Trap:** `ensureCheckerScheduled` filters an **unfiltered** `listJobs()` by name and `cron`. Carried into a Web build that declares the cron, `'reset'` mode would cancel the declared `DEVVIT_JSON` job and replace it with a `USER` one. `'heal'` mode would treat the declared job as the one to keep and cancel the other copies, including the leftover `USER` job, in arbitrary list order. Neither mode is safe to keep as it is.

## What retiring `ensureCheckerScheduled` requires

1. **Declare the cron.** Add `"check_new_episodes": { "endpoint": "/internal/scheduler/check-new-episodes", "cron": "*/30 * * * *" }` under `scheduler.tasks`. Keep the name `check_new_episodes`. Then pending one-off manual runs (`runAt`), and any leftover job that fires before cleanup, still find a handler.
2. **Cancel the leftover once, from app code.** In the Web `onAppUpgrade` handler, call `scheduler.listJobs([ScheduledActionManager.USER])`, keep entries with `name === 'check_new_episodes' && 'cron' in job`, and `cancelJob` each one. Do **not** use an unfiltered `listJobs()`, which would also return, and cancel, the declared `DEVVIT_JSON` cron. The step is idempotent and cheap. [INFERENCE] Keep it until every install has upgraded at least once; leaving it in permanently does no harm.
3. **Delete the workaround.** Remove `src/checkerSchedule.ts`; the `'reset'` call in the AppInstall/AppUpgrade trigger; the `'heal'` calls in the four menu handlers and the `PostSubmit`/`CommentSubmit` trigger, which exists only to heal. Also remove the Redis keys `episode_checker_job_id` and `episode_checker_verified_at` (`redis.del` in the upgrade cleanup, or let them go stale).
4. **Accept or replace the self-heal.** With the workaround gone, the checker exists only if `AppInstall`/`AppUpgrade` fired. That is the same dependency the current code was written to avoid. Options:
   - (a) Accept it. A failure appears in `devvit logs` as a missing `Cron task 'check_new_episodes' scheduled.` line. The fix is to re-upload or upgrade, which reruns reconciliation.
   - (b) Keep a narrow fallback. From a mod menu, check `listJobs([ScheduledActionManager.DEVVIT_JSON])`. If no `check_new_episodes` cron exists, create a `USER` cron. Step 2's cleanup removes it on the next upgrade. App code cannot create a `DEVVIT_JSON` job, so a fallback is always a `USER` job that the app must clean up itself.
   - Which option to take is a design decision for the migration ticket; nothing found forces either.
5. **Never remove the last cron task** without explicit cancel code (see question 2).

## Unconfirmed / gaps

- Whether the scheduler service rejects `cancelJob` on a `DEVVIT_JSON` job created by another manager. The client sends no manager; the template cancels such jobs through the same public client, which suggests the service allows it.
- Whether declared crons count toward the 10-recurring-action limit. [INFERENCE: yes]
- How reliable `AppInstall`/`AppUpgrade` delivery is on Devvit Web, compared with the Blocks behaviour that prompted the heal logic. No first-party statement found.
- Ghost schedules after uninstall/reinstall ([reddit/devvit#239](https://github.com/reddit/devvit/issues/239)) apply to declared crons and cannot be fixed from app code.
- The cron time zone is not documented. It does not matter for `*/30`.
